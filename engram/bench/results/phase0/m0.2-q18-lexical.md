# M0.2 / Q18: the lexical arm, pg_search BM25 or TsvectorIndex (PLAN.md section 11.2 Q18, N76, N131)

Decision proposed for CONFLICTS.md (see `docs/briefs/reports/M0.2-report.md`): **pg_search stays the MVP lexical
arm.** On the real ParadeDB image, as `engram_app` under RLS, the BM25 arm keeps the Top-K pushdown, one partition and
the composite-PK key field, but ONLY in one query shape, and its latency budget is met only behind a SECURITY DEFINER
function. `TsvectorIndex` is not declared the MVP arm: it needs the same kind of function, it is not BM25, and its
latency is worse for every query class except rare terms.

## Environment and data

- Image `paradedb/paradedb@sha256:7aba4dbac45cfcaaaddce50feb7081b3fc907061834c68b52a23aa7b66442b76`: PostgreSQL 16.15,
  pg_search 0.26.0, pgvector 0.8.6. The reference DDL was written for pg_search 0.25; 0.26 prints

  and otherwise accepts the DDL unchanged (the first index column is the key).
- Host: 4 vCPU Intel Xeon 2.1 GHz VM shared with other build sessions. **Load average was 4 to 12 during every run
  (a TLC model checker of another milestone ran on 2 to 3 cores), so absolute milliseconds are inflated; compare
  ratios, and repeat the numbers on idle hardware in M0.6.** The T3 latency gates skip enforcement above load 1/CPU.
- 16 hash partitions, `facts` with the schema's `facts_bm25` index. Namespace `big`: 50,000 facts (50 documents of
  1,000), all in one partition (2 Tantivy segments); namespace `small`: 1,000 facts in another partition. Fact text:
  12 words from a 2,000-word vocabulary `w1..w2000` drawn with `power(random(), 2.5)` (low ranks are frequent: `w1` is

  terms: rare = 2 terms of rank 500-2000, mixed = 1 term of rank 1-60 + 2 of rank 100-2000, common = 3 terms of rank
  1-60. Each cell is 150 queries after 10 warm-up runs, one read transaction each (BEGIN, scope GUCs, query,
  ROLLBACK), `LIMIT 150`, `engram_app` with the scope set.

## What the plan shape does under RLS (the exit criterion)

`EXPLAIN (ANALYZE)` as `engram_app` with `engram.namespace_id` set, `TestLexical_TopKPushdown` and
`TestPlans_AsEngramApp` pin these:

1. **Top-K pushdown holds under RLS in the RLS-shaped form.** The inner Top-K of the arm of PLAN.md 3.8 written with
   `namespace_id = current_setting('engram.namespace_id')::uuid` (the very text of the policy) plans as
   `Merge Append` over `Custom Scan (ParadeDB Base Scan)` with `Exec Method: TopKScanExecState`, `Scores: true`,
   `TopK Order By: pdb.score() desc, memory_id asc`, `TopK Limit`, `Subplans Removed: 15` (one partition of 16) and
   the namespace as a Tantivy `term` clause. The secondary `ORDER BY memory_id` tiebreak is pushed down too, and the
   composite-PK key field (`memory_id`, the non-partition half) is accepted on the hash-partitioned table.
2. **A literal or bound namespace predicate defeats the pushdown.** With `namespace_id = $1` (or a literal) next to the
   RLS qual, the planner prunes at plan time and the policy qual becomes a `Result` node with a One-Time Filter between
   the scan and its `ORDER BY pdb.score()`; the scan then reports `Scores: false` and the statement fails at run time
   with `ERROR: Unsupported query shape` (SQLSTATE XX000). `engramlint sql` must therefore accept
   `namespace_id = current_setting('engram.namespace_id')::uuid` as the explicit predicate of this arm.
3. **`mentioned_at <= 'infinity'` fails** (`json cannot be converted to term`): an unset `as_of` must omit the
   predicate; a finite bound is pushed down as a Tantivy range.
4. **Planning is expensive in the RLS-shaped form.** The namespace is only known at executor start, so the planner
   plans the custom scan of all 16 partitions: about 40 to 80 ms of planning against about 2 ms
   when a literal namespace prunes to one partition; execution is 15 ms either way. This is what separates column A
   from column B below. A generic plan (`plan_cache_mode = force_generic_plan`) removes the planning but not the
   cost: it executes in 46 ms because the query text becomes a run-time expression of the scan.
5. **Scores are per partition.** IDF and average length come from the partition's index: the same fact text scored
   25.0 in one partition and 31.8 in another. Ranking inside a namespace is deterministic (two runs return the same
   150 ids, tested), raw scores are comparable only inside one partition, which is why PLAN.md 3.8 reports normalised
   values only (F-28).
6. Not applicable after D22/N113: `text[]` tag literals and a `tag_count = 0 OR ...` disjunct are no longer in the
   index or the query (tags live on `documents` only); the over-fetch plus outer visibility filter that replaced them
   keeps the pushdown (tested with a tombstoned document).

## Reading

- A is at the arm budget on this loaded host: p95 50-61 ms across classes and sizes (budget 60 ms for the BM25 arm,
  PLAN.md 8.4.4), p50 39-44 ms, dominated by the planning of 16 partitions. It meets the Top-K pushdown criterion; the
  p95 criterion is not certifiable here.
- B is 2.5 to 3 times faster for the 50,000-fact namespace (p50 15-18 ms, p95 23-25 ms). For the 1,000-fact namespace
  it is 31 ms: pg_search has a fixed cost per query of about 15 ms of execution plus planning even for a few
  hundred matching documents.
- C beats everything for rare terms and small namespaces (0.2-5 ms) and loses for frequent terms: mixed p95 80 ms,
  common p95 162 ms and p99 about 290 ms at 50,000 facts, because `ts_rank_cd` must be evaluated for every matching
  row (a frequent term matches 20 to 40 % of the corpus). It is not BM25 (no length normalisation or IDF
  saturation), and the retrieval-quality cost is not measured here (LongMemEval, M0.5/M1.2).

## Decision (proposed)

1. Lexical arm for the MVP = pg_search BM25, in the RLS-shaped form of `lexicalArm` in
   `internal/store/plans_integration_test.go` (finite `as_of` only, no literal namespace predicate).
2. Propose a SECURITY DEFINER `engram_lexical_facts(ns, query, limit[, as_of])` (N131 style: re-checks the namespace in
   scope, owner `engram_migrate`, `EXECUTE` to `engram_app` only) as the production form of the arm if M0.6 on idle
   hardware confirms that A misses the 60 ms p95; it is not in the migrations, because it is a new function the register
   does not list. Adding it later is an expand-only migration.
3. `TsvectorIndex` stays the documented fallback and is **not** declared the MVP arm. If pg_search is dropped, it needs
   the same definer function, and the frequent-term latency above (p95 80-160 ms at 50 k facts) is its p95.
4. M0.6 repeats this on idle hardware, with 100 k-1 M fact namespaces and several namespaces per partition.

## Fix round 1 additions (M0.2 review F2, F7, F9)

- **What is gated (F2).** `TestLexical_TopKPushdown/latency_rls_shaped_form` gates the SHIPPED RLS-shaped arm at p95 <
  60 ms on the 50,000-fact namespace (PLAN.md 8.4.4); `definer_wrapper_candidate` gates the candidate at the same
  budget but the candidate is not in the migrations, so it remains a measurement that informs the decision. On the
  loaded host of this round the shipped arm measured p50 49.5 ms, p95 67.5 ms at load 6.4 on 4 CPUs, so the gate was
  skipped, visibly (F7: above load 1 per CPU the latency gates `t.Skipf`; they never log and pass; the structural
  assertions run in every case).
- **Scope of the trigram gate (F9).** The `engram_entity_fuzzy` gate (p50 <= 10 ms over 85,000 entities) proves the plan
  shape for a trigram-selective name (`kestrel corp` shares its trigrams with no other entity: p50 2.4 ms, p95 2.8
  ms). A name whose trigrams occur in most entities (`entity 5a1` against names `entity NNNNN`) takes the same GIN
  index but rechecks nearly every row: 346-360 ms through the wrapper. That figure is recorded by the test, not
  gated; realistic entity names are measured in M0.6.
