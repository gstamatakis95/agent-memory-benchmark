# M0.2 / Q9: pgx query execution mode behind pgbouncer (PLAN.md section 11.2 Q9)

Question: protocol-level prepared statements (pgx `CacheStatement`, needs pgbouncer >= 1.21 and
`max_prepared_statements`) or no server-side statements (`Exec`, `SimpleProtocol`), per query ~0.2 ms and a pgbouncer
version floor.

Decision proposed for CONFLICTS.md: **`pgx.QueryExecModeExec` for every pool that goes through pgbouncer** (the API
`engram_app` pool and the worker pool); the default `CacheStatement` only for the direct connections (relay, mover,
subject leases, `engramctl`). Reasons: the mode works on every pgbouncer configuration and version in transaction
pooling, it costs at most 0.2 ms at p50 against `CacheStatement` and that is within the noise behind pgbouncer, and
the arms cannot use the main benefit of prepared statements anyway (below).

## Method

pgbouncer 1.26.0 (`edoburu/pgbouncer@sha256:9c78945868a6a142c7fc40ccd843bbe5a606df163c7ffce4de70e0d628d696a2`),
`pool_mode = transaction`, `auth_type = scram-sha-256`, `default_pool_size = 20`, in front of the ParadeDB container
(`paradedb/paradedb@sha256:7aba4dbac45cfcaaaddce50feb7081b3fc907061834c68b52a23aa7b66442b76`), twice: with
`max_prepared_statements = 0` (protocol-level prepared statements unsupported) and `= 100`. All five pgx modes
(`CacheStatement`, `CacheDescribe`, `DescribeExec`, `Exec`, `SimpleProtocol`) against `direct`, `bouncer mps=0` and
`bouncer mps=100`, on five statement shapes: the fence read (one uuid parameter), a fact by key, an
`ANY($2::text[])` filter with a 50-element array, the exact semantic scan over 1,000 `halfvec(768)`
vectors (a 768-element vector parameter), and the lexical Top-K of Q18 (text parameter, 50,000 facts). Each cell is 100
read transactions after 20 warm-up runs, one connection, every transaction = BEGIN, `set_config` of the three scope
GUCs, the statement, COMMIT; the figure is the whole transaction in ms. Load average 3.8-4.6 on 4 CPUs (see
the Q18 note).

## Reading

1. **`CacheStatement` (pgx's default) is unsafe behind pgbouncer without `max_prepared_statements`.** With 0 it failed
   with `prepared statement "stmtcache_..." already exists` as soon as a second client session was routed to a server
   connection that an earlier session had used (the first cell passed only because it had a fresh server connection):
   the named statements leak between the pooled server connections. With `max_prepared_statements = 100` (pgbouncer
   >= 1.21) it works. A deployment that forgets the setting, or an older pgbouncer, breaks queries at random: that is
   the version floor the question asks about.
2. `CacheDescribe`, `DescribeExec`, `Exec` and `SimpleProtocol` work in all three setups, including the 768-element
   vector, the text array and the text parameter of the lexical arm.
3. **Latency differences are within noise.** On the smallest statement, `CacheStatement` and `SimpleProtocol` take
   0.2 ms against 0.4 ms for the other modes directly; behind pgbouncer with prepared statements enabled the order
   changes (`CacheStatement` 0.4, `Exec` 0.6, `SimpleProtocol` 0.8 ms) and with `max_prepared_statements = 0` `Exec` and
   `SimpleProtocol` are 0.3 ms. For the statements that matter (exact semantic 1.2-2.2 ms, lexical 42-47 ms) every mode
   is the same inside the p95 spread. pgbouncer itself costs 0.1-0.3 ms per transaction.
4. **Prepared statements cannot pay back here.** The semantic arm needs `plan_cache_mode = force_custom_plan` (the
   per-namespace partial HNSW is only provable with the namespace and model as constants, N112) and the BM25 arm plans
   per call as well (Q18, point 4), so a named statement saves parse analysis only, not planning.
5. `Exec` binds parameters server-side (type OIDs inferred from the statement, text format) in one round trip, so the
   `$1::uuid`-style casts of the arm SQL are required (and present); `SimpleProtocol` interpolates client-side and is
   kept as the fallback if a pgbouncer configuration ever rejects the extended protocol.

## Decision (proposed)

- Pools behind pgbouncer: `DefaultQueryExecMode = pgx.QueryExecModeExec`; no pgbouncer version floor, no
  `max_prepared_statements` requirement. `config lint` should assert that the DSN mode is not `CacheStatement` for a
  pooled DSN unless `max_prepared_statements > 0` is configured.
- Direct connections keep pgx's default.
- Revisit in M1.2 when the real arm SQL exists, with the arm transactions of N164 under 50 QPS.
