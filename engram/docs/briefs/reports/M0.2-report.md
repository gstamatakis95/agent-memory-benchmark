## Proposed CONFLICTS.md entries (the orchestrator folds these in; I do not edit CONFLICTS.md)

### Q18: the lexical arm is pg_search, in one query shape; its p95 budget needs a definer function (proposed ruling)

- What: PLAN.md 11.2 Q18, N76, N131, 8.4.4 `TestLexical_TopKPushdown`, the M0.2 exit criterion.
- Measurement (`bench/results/phase0/m0.2-q18-lexical.md`; image digest `7aba4d...`, pg_search **0.26.0**, 16
  partitions, 50,000-fact and 1,000-fact namespaces, 150 queries per cell, load average 4-12 on 4 CPUs):
  1. Top-K pushdown under RLS holds **only if** the inner query's namespace predicate is textually the RLS qual,
     `namespace_id = current_setting('engram.namespace_id')::uuid`. With a literal or bound `namespace_id = $1` next
     to the policy, the qual becomes a `Result` node under the Top-K, `Scores: false`, and the statement fails with
     `Unsupported query shape`. `mentioned_at <= 'infinity'` fails (`json cannot be converted to term`): an unset
     `as_of` omits the predicate. The composite-PK key field, the `memory_id` tiebreak and one-partition pruning work.
  2. That shape plans all 16 partitions (about 40-80 ms of planning): p50 39-44 ms, **p95 50-61 ms** against the 60 ms
     budget, i.e. at the budget on a loaded host. Behind a `SECURITY DEFINER` function that takes the namespace as a
     parameter (like `engram_entity_fuzzy`): 50 k facts p50 15-18 ms, **p95 23-25 ms**; 1 k facts p50 31 ms, p95 43-47
     ms.
  3. TsvectorIndex is unusable under RLS without a function as well (`@@`, `ts_rank_cd` are not leakproof: a 217-373
     ms seq scan); behind a function: rare terms 4 ms, but mixed p95 80 ms and common p95 162 ms (p99 about 290 ms) at
     50 k.
  4. Scores are per partition (the same text scored 25.0 and 31.8 in two partitions); rankings inside a namespace are
     deterministic. The `text[]` tag literal and the `tag_count = 0 OR` disjunct of the Q18 text no longer exist
     (D22).
- Readings: (a) pg_search as is; (b) pg_search behind a definer function; (c) TsvectorIndex.
- Proposed resolution: (a) is the MVP arm with the RLS-shaped predicate (the criterion "keeps Top-K pushdown under
  RLS" holds); add the definer function `engram_lexical_facts(ns, query, limit[, as_of])` by an expand-only migration
  in M1.2 if M0.6 on idle hardware confirms the p95 miss; do not declare TsvectorIndex. `engramlint sql` must accept
  the RLS-shaped predicate as the explicit `namespace_id` predicate of N19 for this arm.
- Needs from the human: a register row for the definer function (an N131 extension), or an explicit acceptance of a
  50-60 ms BM25 p95.
- Register rows: N76, N131, N19, D7.

### Q9: pgx `QueryExecModeExec` behind pgbouncer (proposed ruling)

- Measurement (`bench/results/phase0/m0.2-q9-pgx.md`): pgbouncer 1.26.0, transaction pooling, five pgx modes x three
  targets x five statement shapes. The default `CacheStatement` fails behind pgbouncer without
  `max_prepared_statements` (`prepared statement "stmtcache_..." already exists`); every other mode works everywhere;
  latency differences are 0.1-0.4 ms on small statements and nil on arm-sized ones; prepared statements cannot save
  planning because the arms need `force_custom_plan` (N112) and the BM25 arm plans per call.
- Proposed resolution: `QueryExecModeExec` for the pooled (pgbouncer) pools, the default for direct connections; no
  pgbouncer version floor; `config lint` rejects `CacheStatement` on a pooled DSN unless `max_prepared_statements >
  0`.
- Register rows: none (closes Q9; to become a register row).

## What is not proven here

- **Latency gates on idle hardware.** The machine had load 4-12 on 4 CPUs (a TLC run of another session) during every
  measurement. The T3 latency gates (`latencyFailure`) `t.Skipf` (visibly, never log-and-pass) when
  load exceeds the CPU count; structural assertions always run. In the last run the shipped arm measured p95 67.5 ms
  at load 6.4, so its 60 ms gate was skipped and is not certified. The p95 verdicts are therefore "at the budget",
  not certified; M0.6 repeats them.
- **The testcontainers-go default path (bridge network, mapped port) is unexercised** here; only the host-network path
  and `ENGRAM_TEST_PG_DSN` were run.
- After merging main (M0.1), the full `make lint` (buf, vet, golangci-lint with depguard and `lll`, method count,
  line length) and `make test-unit` run and are green.
- pgbouncer was measured at 1.26.0 only (the image available), not the production version.
- `TestIso_Ownership_Transitions` (the edge matrix) is not in this brief; `TestOwnership_ReadyState` pins `ready`, its
  guards and the roles. Behavioural tests of `engram_relay` and `engram_move` (beyond the canary, the grants and the
  self-checks) belong to M1.4 and M1.5.
- The index runner daemon (`engramctl index run`: lease, `vector_indexes` machine, `backend_xmin` guard,
  `TestIndex_RunnerLifecycle`) is not built; `engramctl index` has the partitioned-index procedure and the
  per-namespace `hnsw` statements it will use.
