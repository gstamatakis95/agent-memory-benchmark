### F1 (Major) The PR job cannot finish when a change touches Derivation, Durability or ShardMove

- Finding: the step `scripts/formal-run.sh changed` runs every nightly-tier configuration of a touched specification
  (30-minute cap each) inside a job with `timeout-minutes: 30`, so any pull request that touches `ShardMove.tla`,
  `Durability.tla`, `Derivation.tla`, one of their configurations or one of their mapped test files
  (`internal/move/*_test.go`, `internal/catalog/*_test.go`, `internal/intent/*_test.go`, `internal/expunge/*_test.go`,
  ...) is cancelled red; these are exactly the M1.5, M1.9, M1.10 and M2.1 pull requests.
- Evidence: wall seconds of the committed logs per touched specification: ShardMove 763 + 296 + 458 + 1801 + 27 + 55 +
  26 = 3426 s (57 min); Durability 1801 + 1122 + 60 + 45 + 24 + 25 = 3077 s (51 min); Derivation 754 + 845 + 536 + 21
  = 2156 s (36 min); each before the quick run, the trace proof and the setup of the same job.
- Fix: move `changed` into its own job (or a matrix of one configuration per job) with a timeout above the sum of
  its caps, or restrict it to changes of the specification and its configurations and say so in a CONFLICTS entry.

### F2 (Major) Twin milestones are per specification, not the milestone that builds the twin

  and section 10.2 names many of these tests in other milestones' exits. The pending check then fires at the wrong
  milestone: falsely (the twin cannot exist yet) or late (the twin was due earlier).
- Evidence (test, manifest milestone, milestone whose section 10.2 exit names it): false failures at closure:
  `TestMove_FailoverBelowFloorRefused` (`ShardMove_LaggingFailover`) M1.5 / M1.7; `TestPageRefresh_CommitRetry`
  (`Derivation_CasBeforeIdem`) M2.1 / M3.1; `TestAsOf_ObservationVersions` (`Derivation_EffCited`) M2.1 / M2.3. Late:
  `TestDelete_TenantAckAfterFence` (`Durability_CatalogRestoreInFenceWindow`, N188 costs it in M1.3) M1.9 / M1.3;
  `TestInvalidate_RestoreExact`, `_ConcurrentReextract`, `_RepeatedReusesTag`, `_SurvivesChunkPurge`,
  `TestExpunge_SweeperFindsUnmaterialized`, `TestDelete_ReuseDocumentID`, `TestVisibility_AllSurfaces` M2.1 / M1.3;
  `TestExpunge_Stages` M2.1 / M1.10; `TestReextract_Rebuilds` M2.1 / M1.1; `TestCatalog_ReconcileIgnoresIncomingEpoch`
  M1.5 / M0.3; `TestContent_InsertOnly` M3.1 / M0.2, and it already exists on `main`
  (`internal/store/content_integration_test.go:28`, M0.2 `done`), so `Storage_Update` and `Storage_PurgeUnmarked`

  specification), reject a milestone that is not in PROGRESS.md, and pair the rows whose test exists on `main` when
  the branch merges it (or record why `TestContent_InsertOnly` is not yet the `faultinject` twin).

### F3 (Major) The pinned jar comes from a moving nightly build, not TLC 2.18

- Finding: the download source `releases/download/v1.8.0/tla2tools.jar` is a rolling asset rebuilt from `master`;
  the pinned hash matches the build of 2026-10-06 only, so once upstream republishes, every runner without the cache
  (a cache miss or a 7-day eviction) refuses the jar (rc 2) and the PR and nightly jobs fail with no source for the
  pinned bytes. The jar is also not "TLC 2.18" (section 7, GUARDRAILS); report discrepancy 8 treats this as a banner.
- Evidence: the downloaded asset has `Last-Modified: Tue, 06 Oct 2026 01:47:52 GMT`; its `META-INF/MANIFEST.MF`
  reads `Implementation-Version: 2.0 2026-10-06`, `X-Git-Branch: master`, `X-Git-Revision: 94d0c50...`,
  `Built-By: runner`; TLC prints `TLC2 Version 2026.10.06.014338 (rev: 94d0c50)`.
- Fix: serve the pinned bytes from an immutable location the project controls (or pin an immutable release
  artifact), keep the hash check, and record the version conflict (TLC 2.18 / `de.hhu.stups:tlatools:1.1.0` in section
  7 against the master build named by ENVIRONMENT.md) as a CONFLICTS entry for the orchestrator.
