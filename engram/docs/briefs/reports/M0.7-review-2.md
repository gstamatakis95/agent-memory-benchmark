## Assessment of the state-level replay mode (exit clause 5)

- Why it exists: TLC 2.18 prints `State 2: <Draw line 86, ...>` without the parameter values, so a 2.18 error trace
  cannot be turned into an action-level log. The new mode records each state and generates `TraceReplay == l <= Len /\
  l' = l + 1 /\ Next /\ v' = TraceStates[l].v` for every variable.
- What it proves: the TLC value parser and the TLA+ renderer round-trip every variable of every spec, and the logged
  states form a behaviour of `Next` from `Init`: a reversed log and a log with one step removed both end "No error has
  been found" (rejected). The named invariant is violated after events + 1 states and the prefix is accepted (24 ok).
- What it does not prove: the action names. `TraceEvents[l].act` is not used by the replay, so a fixture whose five
  actions are all renamed `Plan` is accepted and violates `ServedFromIndex` exactly like the real one (finding N2).
- Exit clause 5 ("the converter replays a TLC-produced trace of each spec through `TraceNext`") is still met through
  the six action-level fixtures (`<Spec>.trace.jsonl`), which are TLC-produced (the earlier build, whose headers carry
  parameters), are replayed under 2.18 through the action dispatch by every `proof` run with the same invariant and the
  prefix accepted, and are pinned by `TestFixtures_AreCurrent`. They can no longer be regenerated with the pinned
  toolchain, which N2 records.

### N1 (Minor) The fast group is chosen from the last logged wall time, so the worker count flips between runs

- Finding: a configuration joins the parallel one-worker group when its last log says <= 4 s; that number depends on the
  machine load of the previous run, so the same configuration runs with one worker in one run and four in the next,
  and its committed counterexample and counts change with it.
- Evidence: two consecutive runs of six fast must-fail configurations: five produced identical logs (one worker,
  deterministic, as claimed), `ShardMove_ReadyBeforeIndex` switched to `workers=4` in the second run (its quick-run log
  read 5 s under load) and its counts went from 132/57 to 192/85. The verdict was OK both times.
- Fix: list the fast group in `MANIFEST.md` (or derive it from the shipped table), not from the last log.

### N2 (Minor) The state-level replay ignores the action names
