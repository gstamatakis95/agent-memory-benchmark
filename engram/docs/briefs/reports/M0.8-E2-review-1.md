### F2 (Major): the rendered ownership statements are not executable against the DDL

- Finding: `ownership-transitions.md` renders each edge from the table columns only and drops the per-edge column rules
  the trigger enforces, so `ready_target` and (for a row that carries a floor) `return_move` are refused by the DDL they
  claim to render, and `freeze_delete` omits its `move_id IS NULL` precondition; §3.3.1 says "the statements of §5.5
  are generated from this table", and M1.8 will copy them.
- Evidence: rendered `ready_target` is `UPDATE namespace_ownership SET state = 'ready' WHERE … state = 'incoming' AND
  epoch = $epoch;`. The DDL has `CHECK (state <> 'ready' OR floor_lsn IS NOT NULL)` and `CHECK (state <> 'ready' OR
  w_final IS NOT NULL)` (`migrations/shard/0001_init.sql:626-627`), the INSERT path refuses a non-null `floor_lsn`
  (`:390`) and the trigger raises when `edge = 'ready_target' AND NEW.floor_lsn IS NULL` (`:440`): an `incoming` row
  has `floor_lsn` NULL, so the rendered statement always fails with 23514. Rendered `return_move` sets no `floor_lsn =
  NULL` while the trigger refuses `edge = 'return_move' AND NEW.floor_lsn IS NOT NULL` (`:441`); §3.3.1 says
  `return_move` "clears `floor_lsn`" and `ready_target` "stamps `floor_lsn`". `freeze_delete` renders no `AND move_id
  IS NULL` although §3.3.1 and the row's own note require it. The edge table itself (30 rows, 20 edges) matches the
  `INSERT INTO ownership_transitions` rows and §3.3.1 row by row (role sets, from/to states, epoch rules, move and
  target effects).
- Fix: render the trigger's column rules per edge (`ready_target`: `floor_lsn = $copy_end_lsn, w_final = $w_final`;
  `return_move`: `floor_lsn = NULL`; `freeze_delete`: `AND move_id IS NULL`), and add a gendocs test that every column
  the trigger constrains for an edge appears in that edge's statement (or execute the statements in the T3 skeleton).
